# MFGraph 内容格式（第 1 版）

[English](../content-format.md) | [简体中文](content-format.md)

本文规定 MFGraph 中决定内容 hash 与树 hash 的字节级格式：内容身份、路径文法、manifest 树节点和存储 key。目标是让另一个实现能够独立产生并校验完全相同的 hash。测试向量见 [`testdata/vectors`](../../../testdata/vectors/README.md)。

文中“必须（MUST）/不得（MUST NOT）/应当（SHOULD）/可以（MAY）”按 RFC 2119 理解。

本文以英文版为准；中文译文仅为方便阅读。

本文中任何会改变 hash 的修改都需要新的格式版本（`"format": 2`）；按第 1 版写入的数据始终有效。

## 1. 内容身份

1. 文件的身份是其**原始字节**的 SHA-256。不做任何规范化：只在换行符或 Unicode 规范化形式上不同的两个文件，身份也不同。
2. 身份与存储、传输方式无关：分块边界、分片上传的 part 大小、存储后端、上传路径都不影响身份。
3. 文本形式：`sha256:` 加 64 位**小写**十六进制摘要，例如 `hello` 为 `sha256:2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824`。解析时必须拒绝其他一切写法（大写十六进制、大写前缀、其他算法名、缺少前缀、前后空白、长度不对），保证每个 hash 只有一种表示。
4. 数据库形式：不带前缀的 64 位小写十六进制摘要，另设算法列，取值 `sha256`。
5. 空文件是合法内容，其身份为 `sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`，大小为 0。
6. 内容 hash 与树节点 hash（3.7）的计算方式相同，**没有域分隔**：如果一个文件的字节恰好等于某个节点的规范编码，它的 hash 就等于该节点的 hash。因此使用 hash 时必须先知道它指的是哪一种对象。在树中，种类由位置决定（文件条目的 `hash` 是内容 hash；目录条目和索引引用的 `hash` 是节点 hash），存储也把两者分开（`objects/` 与 `tree/`，见第 4 节）。

## 2. 路径

路径表示文件相对 workspace 根的位置，由 `/` 分隔的若干段组成。目录只作为文件路径的前缀存在（没有空目录）；符号链接不属于数据模型。

2.1–2.3 节是**写入时规则**：服务端对提交新建的名字执行，树的写入方在编码前执行。从已存储的树节点中读出的名字只按 2.5 节的**读取时规则**检查，读取时规则从不依赖 Unicode 数据表。2.6 节说明提交时检查哪些名字，以及如何按路径查找。

### 2.1 规范化

服务端按以下顺序规范化每个路径，第一个失败的步骤决定参考实现报告的错误类别：

1. 输入必须是合法 UTF-8（`invalid_utf8`）且非空（`empty`）。
2. 不得以 `/` 开头（`absolute`）。然后从左到右逐个检查字符，第一个违规的字符决定错误类别：
   * `\`（`backslash`）；
   * 控制字符 U+0000–U+001F、U+007F–U+009F，即 C0、DEL 和 C1（`control_char`）；
   * 非字符：U+FDD0–U+FDEF，以及每个平面的最后两个码位 U+xxFFFE 和 U+xxFFFF，共 66 个（`noncharacter`）；
   * 固定禁止清单中的字符（`disallowed_char`）：双向格式字符 U+061C、U+200E、U+200F、U+202A–U+202E、U+2066–U+2069，以及不可见或破坏排版的字符 U+00AD（软连字符）、U+180E（蒙古文元音分隔符）、U+200B（零宽空格）、U+2028 与 U+2029（行分隔符、段分隔符）、U+2060（词连接符）、U+2061–U+2064（不可见数学运算符）、U+FEFF（零宽不换行空格）、U+FFF9–U+FFFB（行间注释控制符）；
   * 在 Unicode 版本 V 中未分配（通用类别 Cn）的码位（`unassigned_char`；见 2.4）。非字符也属于 Cn，但上一条规则会先把它们报为 `noncharacter`。
3. 转换为 Unicode 规范化形式 C（NFC）。
4. 按 `/` 切段：段不得为空（`a//b`、结尾 `/`：`empty_segment`），不得是 `.` 或 `..`（`dot_segment`）。
5. 每段至多 255 字节（`segment_too_long`），整个路径至多 4096 字节（`path_too_long`），均按 NFC 之后的 UTF-8 字节数计算。255 字节是 Linux ext4（以及大多数 POSIX 文件系统）的文件名上限；85 个汉字（UTF-8 中每个 3 字节）作为文件名已经够用。这一上限也是读取时规则（2.5），所以 format 1 永远不能放宽。

第 2 步的全部字符检查都在 NFC 之前、分段规则之前对原始输入执行；例如 `../a` 后接 U+200B 报 `disallowed_char`，而不是 `dot_segment`。第 3 步的结果就是规范路径。

NFC 可能改变客户端发送的字符：除了把 `e` U+0301 这样的组合序列合成为 `é`，它还会把 CJK 兼容表意字替换为对应的统一表意字（U+FA10 变成 U+585A），日文、韩文的人名地名里常见这类字。只有规范路径会被存储，服务端也只返回规范路径，所以客户端必须使用收到的路径，而不是自己发送的路径。

错误类别只在输入恰好违反一条规则时才是规范性的。输入同时违反多条规则时（例如 `/a//b`，或 `a\b` 后接 U+202E），实现可以报告其中任意一个类别；上面的顺序是参考实现的顺序，记录这一顺序的测试向量标注了 `multiple_violations`。同级名字的规则（2.2）同样如此（例如一组文件里既有重复路径，又有同一个名字既用作文件又用作目录）。输入是否被接受、规范形式是什么，都与顺序无关。

理由：控制字符和双向格式字符会让名字的显示与实际内容不符（显示欺骗，即 "Trojan Source"）；不可见字符会让不同的名字看起来一模一样，行/段分隔符会破坏列表显示；未分配码位尚没有确定的规范化和大小写折叠（见 2.4）；RFC 8785 所依赖的 I-JSON（RFC 7493）禁止非字符。禁止清单是固定的：不会把格式字符（类别 Cf）整类拒绝。它只是写入时规则（2.5）：以后可以扩充，含有这些字符的已存储名字仍然可以读取。

没有其他规则。特别地，以下字符**允许**使用：

* ZWNJ U+200C 与 ZWJ U+200D —— emoji 序列（例如 U+1F468 U+200D U+1F469 U+200D U+1F467）以及波斯文、印度诸文字等都需要它们；
* 变体选择符 U+FE00–U+FE0F —— emoji 的显示形式需要它们（例如 U+2764 U+FE0F）；
* tag 字符 U+E0020–U+E007F —— 地区旗帜 emoji 需要它们（苏格兰旗帜为 U+1F3F4 后接 `gbsct` 对应的 tag 字符和 U+E007F）；
* U+034F 组合字素连接符（COMBINING GRAPHEME JOINER）；
* 全角斜杠 U+FF0F —— 它不是分隔符；
* 私用区字符 —— 它们属于已分配码位（类别 Co）；
* 在某些操作系统上保留或不便使用的名字（`CON`、以点或空格结尾的名字）—— 这类名字的映射交给导出工具处理，不写进格式。

### 2.2 同级名字

同一目录内：

* 同一个名字不得同时用作文件和目录（`file_dir_conflict`）；
* 同一路径不得出现两次——包括只在 Unicode 规范化形式上不同的两个输入（`duplicate`）；
* 两个不同的名字不得具有相同的**折叠键**（`case_conflict`）。

名字的折叠键是 Unicode 标准定义的规范大小写无关形式（第 3.13 节，定义 D145）：

```text
fold_key(name) = NFD(casefold(NFD(name)))
```

其中 casefold 是 Unicode 完全大小写折叠（CaseFolding.txt 中状态为 C 和 F 的映射，不含土耳其语映射 T）。两个名字的折叠键相等即为冲突。折叠键只用于比较，不会存储。例如：

* `Plan.dwg` 与 `plan.dwg` 冲突；`straße` 与 `STRASSE` 冲突（都折叠为 `strasse`）；`σ` 与 `ς` 冲突；
* Cherokee 字母折叠到大写：U+13A0 与 U+AB70 冲突，U+13F0 与 U+13F8 也冲突；
* 格鲁吉亚文 Mtavruli 折叠到 Mkhedruli：U+1C90 与 U+10D0 冲突；
* 外层的 NFD 使折叠键对规范等价封闭：U+1E9E U+0301 与 `s` U+015B 冲突（都得到 `s s` U+0301），U+FB01 U+0301 与 `f` U+00ED 也冲突；
* `İ`（U+0130）与 `i` 不冲突，`ı`（U+0131）与 `I` 也不冲突。

### 2.3 分支名

分支名按单个路径段的规则校验（对一个段执行第 1–5 步），因此永远不含 `/`；出现 `/` 时报 `contains_slash`。保存其 NFC 形式。

同一个 workstream 内，两个分支名不得具有相同的折叠键（2.2），分支 `main` 也算在内：`Dev` 与 `dev` 不能共存，`main` 与 `Main` 也不能。除此之外按字节保存名字：`dev` 与 `dev `（结尾带空格）是两个不同的分支。这条规则现在写入规范；参考实现在支持按名字创建分支时执行检查。

### 2.4 Unicode 版本 V

NFC、大小写折叠和 `unassigned_char` 规则都依赖 Unicode 字符数据库。format 1 固定了这些数据表的版本：**V = 15.0.0**。不论所在平台提供哪个版本，每个实现的写入时规则都必须使用 Unicode 15.0.0 的数据表。（参考实现的通用类别来自 Go 标准库，NFC 与大小写折叠来自 golang.org/x/text；在 Go 1.26 下两者都是 Unicode 15.0.0，工具链升级改变其中任何一个时，测试会失败。）

* 升级 V 的唯一方式是在本文档中记录新的版本号。Unicode 的稳定性政策保证已分配的码位保持已分配，已分配字符的 NFC 与大小写折叠结果不变，因此升级 V 只会让更多码位变为已分配：允许的字符只增不减，原来合法的路径仍然合法，规范形式也不变，已有数据不受影响。
* 由于写入时拒绝所有未分配码位，已存储的名字里不会出现以后版本可能给出不同规范化结果的字符。
* 读取时规则（2.5）从不使用 Unicode 数据表，因此不同的 V（另一个实现，或升级 V 之后）都不会让已存储的数据无法读取。
* 结果依赖 V 的测试向量带有 `"ucd_version": "15.0.0"` 标注：U+1F6DC（Unicode 15.0 新增）被接受；U+2EBF0（15.1 新增）、U+1C89（16.0 新增）和 U+1F6D8（17.0 新增）报 `unassigned_char`。

### 2.5 写入时规则与读取时规则

| 规则 | 写入时（上传、提交、`Build`） | 读取时（解码已存储节点、遍历树） |
|---|---|---|
| 合法 UTF-8，非空 | ✓ | ✓ |
| 名字中不含 `/`；不含 `\` | ✓ | ✓ |
| 不含控制字符（C0、DEL、C1） | ✓ | ✓ |
| 不含非字符（U+FDD0–U+FDEF、U+xxFFFE、U+xxFFFF） | ✓ | ✓ |
| 不含固定禁止清单中的字符（2.1） | ✓ | — |
| 不是 `.` 或 `..` | ✓ | ✓ |
| 每个名字至多 255 字节 | ✓（按 NFC 之后） | ✓（按存储的字节） |
| 每个路径至多 4096 字节 | ✓ | — |
| 不含（V 中）未分配的码位 | ✓ | — |
| NFC | 执行（存储规范形式） | 不检查 |
| 同级名字无大小写折叠冲突 | ✓ | 不检查 |
| 无重名、无"同名既是文件又是目录" | ✓ | ✓（由名字严格升序保证，见 3.8） |

读取时规则是写入时规则的子集，所以符合规范的写入方产生的一切都能读取。读取时规则只包含结构性检查，从不使用 Unicode 数据表，在 format 1 中固定不变。读取方不得因为存储的名字不是 NFC、两个名字折叠键相同、名字含有在读取方 Unicode 版本中未分配的码位、或名字含有固定禁止清单中的字符而拒绝节点。因此写入时规则可以调整（新的 V、更长的禁止清单），而不会让已存储的数据无法读取。测试向量把这类节点列在 `decode_valid_build_rejects` 中。

### 2.6 规则的适用范围

* **提交。** 提交中的每个变更都给出一个路径，先用下面的查找规则在基准快照中查找它。
  * 如果找到了文件，变更就替换或删除这个文件。不对它执行写入时规则：条目保留存储时的名字，即使当前的写入时规则会拒绝这个名字。
  * 否则变更创建这个路径（删除一个找不到的路径会失败）。写入时规则只用于变更新建的名字：路径中在基准快照里不存在的那些段，即新文件以及它上面新建的目录。已经存在的目录用查找规则找到，保留存储时的名字。每个新名字以 NFC 形式存储，并按 2.2 节的同级规则与所在目录中已有的名字比较；新路径（已存储的目录名加上新名字）至多 4096 字节。
  * 从基准快照原样带过来的条目（以及从另一个快照恢复的条目）保留存储时的字节：不重新规范化，也不重新检查。因此，即使树里有不符合当前写入时规则的名字（例如由 V 更高的实现写入、只在以后的 Unicode 版本中才分配的码位），后续提交也不会因为本次没有新建的条目而失败。
* **查找。** 用于查找已有条目的路径（列目录、下载文件、diff 或 restore 中给出的路径，以及替换或删除文件的变更的路径）分四步处理：
  1. 输入必须是合法 UTF-8，非空，不以 `/` 开头，并且不含 `\`、控制字符和非字符（即 2.5 节读取时规则中的字符规则）；
  2. 转换为 NFC；
  3. NFC 形式不得有空段、`.` 段或 `..` 段，每段至多 255 字节，整个路径至多 4096 字节；
  4. 先找路径与原始输入按字节完全相同的条目；找不到时，再找路径与 NFC 形式相同的条目。

  查找不检查未分配码位、禁止清单和大小写冲突。前三步不通过的输入按第一个不满足的规则报错（错误类别同 2.1 节）。按原样给出时一段可以超过 255 字节，只要它的 NFC 形式不超过：30 个 NFD 形式的韩文音节是 270 字节，NFC 形式是 90 字节。不是 NFC 的已存储名字（由其他实现写入）在输入给出它的确切字节时可以找到。测试向量在 `lookup` 中给出这些规则。

## 3. 树节点

快照的内容是一棵由不可变节点组成的树。每个节点以其规范字节的 SHA-256 寻址；根节点的 hash 就是快照的 `root_tree_hash`。

### 3.1 规范编码

节点按 RFC 8785（JSON 规范化方案，JCS）序列化，取值只限于对象、数组、字符串和整数：

* 对象的键排序（所有键都是 ASCII，因此就是字节序）；不得有重复键；
* token 之间没有空白；UTF-8，不带 BOM；末尾没有换行；
* 字符串只转义以下字符：`"` 写作 `\"`，`\` 写作 `\\`，U+0008 写作 `\b`，U+0009 写作 `\t`，U+000A 写作 `\n`，U+000C 写作 `\f`，U+000D 写作 `\r`，其余低于 U+0020 的码位写作 `\u00xx`（十六进制小写）；其他所有字符（包括 `/`、`<`、`>`、`&`、U+007F 和全部非 ASCII 字符）都按原样输出 UTF-8；
* 整数用十进制，不带正负号、前导零、小数和指数，取值范围 0 … 2^53−1。原因：RFC 8785 按 IEEE-754 双精度浮点数（ECMAScript 的 Number 类型）序列化数字，双精度只能精确表示到 2^53−1 为止的全部整数；更大的值在不同的合规实现中可能输出不同的字节。作为文件大小，2^53−1 字节（约 9 PB）远超任何支持的大小。

数组的顺序不由 RFC 8785 规定，由下文规定。

### 3.2 节点类型

每个节点都有 `"format": 1`，并属于以下三种之一。键按表中顺序出现（即 RFC 8785 的顺序）。

| kind | 结构 |
|---|---|
| `dir` | `{"entries":[<条目>,…],"format":1,"kind":"dir"}` —— 一个完整目录 |
| `dir_page` | `{"entries":[<条目>,…],"format":1,"kind":"dir_page"}` —— 大目录的一页（不得为空） |
| `dir_index` | `{"format":1,"kind":"dir_index","pages":[<引用>,…]}` —— 指向页或下一层索引（不得为空） |

一个节点至多 1024 个条目或引用，规范编码至多 1,048,576 字节。

### 3.3 条目

| 类型 | 结构 |
|---|---|
| 文件 | `{"hash":"sha256:<hex>","mode":420,"name":"a.txt","size":1234,"type":"file"}` |
| 目录 | `{"hash":"sha256:<hex>","name":"docs","type":"dir"}` |

* `name` 是一个路径段。写入方存储第 2 节产生的规范（NFC）形式；读取方只按读取时规则（2.5）检查名字。
* 文件可以为空：`size` 为 0，`hash` 为空内容的 hash（1.5）。
* 文件的 `hash` 是其内容身份（第 1 节），`size` 是字节数，`mode` 只能是 `420`（0644，普通文件）或 `493`（0755，可执行）。实现把本地权限中任一执行位置位映射为 `493`，否则为 `420`。不保存其他元数据：没有修改时间、属主和其他权限位。
* 目录的 `hash` 是该目录顶层节点的 hash：`dir` 节点或顶层 `dir_index` 节点，绝不是 `dir_page`。
* 条目按 `name` 的 UTF-8 字节序严格升序排列（这不是 UTF-16 顺序：`｡` U+FF61 排在 `𝄞` U+1D11E 之前）。写入方保证同级名字遵守 2.2 节。
* 条目只在各自的目录内排序，目录名参与比较时不带结尾的 `/`。因此遍历一棵树（先序，每个目录的条目按上述顺序）得到的路径是**路径顺序**：两个路径逐段比较，每段按 UTF-8 字节比较，一个路径排在它下面的所有路径之前。路径顺序不等于完整路径字符串的字节序。例：目录 `a`（含 `x`），以及文件 `a-b` 和 `a.txt`。遍历顺序是 `a`、`a/x`、`a-b`、`a.txt`；完整路径的字节序是 `a`、`a-b`、`a.txt`、`a/x`（`-` 是 0x2D，`.` 是 0x2E，`/` 是 0x2F）。按完整路径字节排好序的列表（例如来自数据库索引）不能直接交给按遍历顺序建树的程序，也不能与树的遍历结果做归并。测试向量：`walk-order-is-path-order-not-full-path-byte-order`。

### 3.4 索引引用

`dir_index` 中的引用为 `{"count":N,"first":"<名字>","hash":"sha256:<hex>"}`：

* `hash` 是一个 `dir_page` 或下一层 `dir_index` 的 hash；
* `count` 是被引用节点下面全部**目录条目**（叶子：文件和子目录）的数量——对 `dir_page` 是它的条目数，对下一层 `dir_index` 是其各引用 `count` 之和。因此顶层索引各引用的 `count` 之和等于该目录的条目总数。由于页和索引都不为空，`count` **至少为 1**；
* `first` 是被引用节点下面第一个目录条目（叶子）的名字——对下一层索引，就是它第一个引用的 `first`。

引用按 `first` 的 UTF-8 字节序严格升序排列。

示例（测试向量 `two-level-index-1048577-entries`）：含 1,048,577 个文件 `f0000000` … `f1048576` 的目录被切成 1025 页（1024 页各 1024 个条目，外加 1 页 1 个条目）。1025 个页引用超过 1024，于是再装进两个一级索引（分别含 1024 个和 1 个引用），顶层索引为：

```json
{"format":1,"kind":"dir_index","pages":[{"count":1048576,"first":"f0000000","hash":"sha256:a3d74c9e09aab22419a4f5d1324793ca517abd5df41ffea1e690fda9ee224095"},{"count":1,"first":"f1048576","hash":"sha256:25568880f10538654d433d8b9a01bd94b6bb770e5464b90a77ba0b4f3c094509"}]}
```

第一个引用覆盖从 `f0000000` 开始的 1024 × 1024 = 1,048,576 个条目；第二个引用覆盖最后一个条目。第二个一级索引为 `{"format":1,"kind":"dir_index","pages":[{"count":1,"first":"f1048576","hash":"sha256:88a61f4436ce70dac4a0b057cf7b092b9e473d970cd61e4404f6d240dea79db6"}]}`，目录的 hash（即顶层索引的 hash）为 `sha256:c63ef4eaae5650368cdb6fac7d9dd85a4d895db54ee8e3bdd17a478bfbd9767c`。

### 3.5 大目录拆分

阈值在第 1 版中固定，不可配置。

```text
layout(entries):                      # entries 已按 3.3 排序
  if len(entries) <= 1024 and size(由 entries 组成的 dir 节点) <= 1048576:
      return node("dir", entries)
  pages = greedy(entries, "dir_page")
  refs  = [ref(count=len(p), first=p[0].name, node("dir_page", p)) for p in pages]
  while len(refs) > 1024 or size(由 refs 组成的 dir_index 节点) > 1048576:
      groups = greedy(refs, "dir_index")
      refs   = [ref(count=sum(r.count for r in g), first=g[0].first, node("dir_index", g))
                for g in groups]
  return node("dir_index", refs)

greedy(items, kind):                  # 保持顺序，依次填满每个节点
  开一个新节点；对每一项：若加入后会超过 1024 项或使节点编码超过 1048576 字节，
  就关闭当前节点、开新节点；然后加入该项。
```

含 `i1…in` 的节点大小即其编码长度：该类型空节点的大小 + 各项大小 + `n−1` 个逗号。空节点编码分别为 38 字节（`dir`）、43 字节（`dir_page`）、42 字节（`dir_index`）。

由此：1024 个条目是一个 `dir` 节点；1025 个条目是一个 `dir_index` 加两页（1024 和 1 个条目）；超过 1024 × 1024 个条目时增加第二层索引。在大目录靠前位置插入名字，会改写其后的各页（第 1 版接受这一点）。

1,048,576 字节的上限作为防御性上限保留在第 1 版格式中，但在第 2 节的路径规则下不可能触发：名字至多 255 字节，且只有 `"` 需要转义（变为 2 字节），所以一个文件条目编码至多 651 字节，1024 个条目约 667 KB 以内，1024 个索引引用约 644 KB 以内。因此第 1 版中拆分总是发生在 1024 项处：**一个目录除最后一页外，每页恰好 1024 个条目**；顶层以下的索引除最后一个外，每个恰好 1024 个引用，读取方可以单独校验一页。没有测试向量能覆盖字节上限；实现应当用调低阈值的单元测试来测它（参考实现就是这样做的）。

### 3.6 根与空目录

根是 `dir` 或 `dir_index` 节点。只有根可以为空，此时为 `{"entries":[],"format":1,"kind":"dir"}`（hash `sha256:e515bab4a24abb9c4929143865d247855e153af697b270afb65a0dcb1b62d9c4`）。指向空节点的目录条目是非法的。

### 3.7 节点 hash

节点 hash 是其**未压缩**规范字节的 SHA-256，采用第 1 节的文本形式。节点如何压缩、存在哪里都不影响 hash。节点 hash 与内容 hash 没有域分隔（1.6）。

### 3.8 严格解码

读取方必须拒绝节点，除非以下条件全部满足：

1. 不超过 1,048,576 字节，是合法 UTF-8，是单个 JSON 对象，键与其类型完全一致，`format` = 1，`kind` 已知；
2. 条目和引用的键与其类型完全一致；名字和 `first` 满足读取时规则（2.5）；hash 为规范形式；mode 为 420 或 493；整数在范围内（0 … 2^53−1，且 `count` 至少为 1）；不存在 symlink 或其他类型；
3. 名字（以及 `first`）按 UTF-8 字节序严格升序——这同时排除了重名和"同名既是文件又是目录"；`dir_page` 和 `dir_index` 不为空；
4. 按 3.1 节重新编码解码结果，得到与输入完全相同的字节，并且字节的 SHA-256 等于期望的 hash。

遍历整棵树的读取方还必须检查：除根以外没有空目录；每个引用的 `count` 和 `first` 与被引用节点一致；一个目录所有页中的条目整体严格升序；每个分页目录的拆分方式与 3.5 节完全一致。读取方不检查 NFC、大小写折叠冲突、未分配码位和固定禁止清单（2.5）。以上规则合在一起，保证每个目录清单只有唯一一种合法编码；写入时规则保证等价的名字不会同时存在。

### 3.9 示例

只含一个文件 `a.txt`（内容为 `hello\n`，6 字节）的树：

```json
{"entries":[{"hash":"sha256:5891b5b522d5df086d0ff0b110fbd9d21bb4fc7163af34d08286a2e846f6be03","mode":420,"name":"a.txt","size":6,"type":"file"}],"format":1,"kind":"dir"}
```

它的 hash（也就是根 hash）为 `sha256:c054d695dcf341ac6d5570a0a7e0c1cbcf14379854ea857a1643c9bddf34695a`。

## 4. 存储 key

对象存放在由 hash 推导出的 key 下。`<hex>` 是 64 位小写 SHA-256，`<hh>` 是它的前两个字符。

| 对象 | 相对 key |
|---|---|
| 文件内容 | `objects/<hh>/<hex>` |
| 树节点 | `tree/<hh>/<hex>.json.zst` —— 规范字节经 zstd 压缩后存储；`<hex>` 是未压缩字节的 hash |

* 完整对象 key = `<storage_prefix>/<相对 key>`。数据库只保存相对 key。
* `storage_prefix` 在创建 workspace 时确定，之后不再改变。它非空，没有首尾 `/`；按 `/` 分出的每一段都非空、至多 255 字节，只由 ASCII 字符 `A`–`Z`、`a`–`z`、`0`–`9`、`.`、`_` 和 `-` 组成，不是 `.` 或 `..`，也不以 `.` 结尾。（255 字节是常见文件系统的文件名上限；Windows 文件系统和 SMB 共享会去掉名字末尾的点，`a.` 和 `a` 在那里会成为同一个目录。）
* 前缀至多 **942 字节**，以保证每个完整 key 都不超过 Amazon S3 的 1024 字节 key 上限。最长的相对 key 是树节点的 key，连同分隔符共 82 字节：

  ```text
  "/tree/" + <hh> + "/" + <hex> + ".json.zst"  =  6 + 2 + 1 + 64 + 9  =  82
  1024 - 82 = 942
  ```

  （`/objects/<hh>/<hex>` 为 76 字节。）
* 同一个存储后端上各 workspace 的前缀不得冲突：按 ASCII 不区分大小写比较，任何前缀都不得与另一个相同，也不得是另一个按 `/` 划分的上级路径。`tenants/A` 与 `Tenants/a` 冲突，`a` 与 `a/b` 冲突，`a` 与 `ab` 不冲突。理由：对象按前缀列出（例如垃圾回收），有些后端不区分大小写，冲突会让一个 workspace 看到甚至删除另一个 workspace 的对象。
* project 级 workspace 的默认前缀为 `tenants/<tenant_id>/projects/<project_id>/workspaces/<workspace_id>`，其中各 ID 是 ULID（26 个大写字符）。默认前缀满足以上所有规则，彼此之间也从不冲突。宿主平台可以选择满足这些规则的其他前缀。
* 内容对象不在 workspace 之间共享。

### 4.1 存储布局的演进

key 布局属于 format 1 的一部分。以后更换 hash 算法或压缩方式时，在 `objects/` 和 `tree/` 旁边**新开顶层目录**；现有 key 永远不修改、不移动、不复用，format 1 写入的数据保持原位。

树节点对象是一个标准 zstd 帧（RFC 8878）：

* 写入方必须只写一个帧，不使用字典，并在帧头写 `Frame_Content_Size`。（单段帧总是带有这个字段，参考写入方设置 `Single_Segment_flag`；有些编码器如果不专门设置，小帧就不写大小。）
* 读取方必须接受窗口至多 **8 MiB**（8,388,608 字节；RFC 8878 建议解码器支持至多 8 MB 的窗口）的每一个帧，无论是否带 `Frame_Content_Size`；并且必须把输出限制在 **1,048,576 字节**（3.2 节的节点大小上限）：解压到这里就停止。单段帧的窗口就是它的 `Frame_Content_Size`。
* 两个上限相互独立。窗口取决于对象是怎样压缩的，而不是节点的大小：不知道输入大小的流式压缩器，即使压缩 38 字节的空根，通常也声明 2 MiB 或更大的窗口。读取方不得因为窗口大于输出上限而拒绝一个帧。
* 读取方必须拒绝以下对象：窗口超过 8 MiB；解压结果超过 1,048,576 字节（这同时防御解压炸弹）；需要字典。之后校验未压缩规范字节的 hash（3.7），不一致也必须拒绝。

## 5. 核对一个实现

* `testdata/vectors/contenthash.json`、`pathx.json` 和 `tree.json` 给出输入和期望结果；生成规则见 [向量说明](../../../testdata/vectors/README.md)。这些文件是纯 ASCII：所有非 ASCII 字符都写成 `\u` 转义。

* `mfgraph debug tree <目录> --out <输出目录>` 打印本地目录对应树的每个节点，并把每个节点的规范字节写成 `<输出目录>/<hex>.json`；对这些文件运行 `shasum -a 256`，结果必须与文件名一致。
